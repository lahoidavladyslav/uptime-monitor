# Новий фронтенд (SPA) для Uptime Monitor — дизайн

Дата: 2026-11-12. Статус: **чернетка, чекає затвердження**.

## 1. Навіщо

Зараз інтерфейс — серверні Django-шаблони на «голому» Bootstrap без власного дизайну. Власник проєкту хоче
**окремий фронтенд у власній директорії**, із сучасним дизайном, і щоб «усе співпадало» з бекендом:
жодних розбіжностей між тим, що віддає сервер, і тим, що очікує інтерфейс.

Що з цього випливає: бекенд не має API, тому спершу потрібен JSON-API з машинно-перевірюваним контрактом.

## 2. Цілі

- Окремий SPA в `frontend/` (той самий репозиторій), повний паритет функцій зі старим інтерфейсом.
- **Контракт, що не може розійтися:** OpenAPI-схема бекенду → автогенеровані TypeScript-типи → збірка
  фронту падає, якщо типи застарілі (перевірка в CI).
- Сучасний вигляд: світла й темна теми, адаптивність від 360 px, швидке відчуття (оптимістичні оновлення,
  скелети завантаження), доступність (клавіатура, контраст WCAG AA).
- Нічого не втратити в безпеці: сесійні cookie + CSRF, 2FA, підтвердження email, скидання пароля, SSRF-захист.

## 3. Не цілі

- Не переписувати бекенд-логіку (перевірки, інциденти, SSL, звіти) — API лише відкриває її.
- Не робити мобільний нативний застосунок, не додавати WebSocket/SSE (поки опитування).
- Не прибирати старий Django-інтерфейс до паритету; публічні статус-сторінки лишаються серверними.
- Не вводити i18n-фреймворк: інтерфейс українською, рядки зібрані в одному модулі, щоб потім можна було
  локалізувати.

## 4. Антицілі (провал, навіть якщо «технічно працює»)

- Дві різні реалізації однієї валідації (форма Django і API розходяться).
- Токени в `localStorage` або відкритий CORS.
- Фронт, що ламається тихо при зміні API.
- Вигляд «шаблонного дашборда з усім підряд»: щільність інформації має допомагати, а не лякати.

## 5. Обмеження

- Бекенд: Django 5.2, Python 3.12, Postgres, Celery/Redis — без змін архітектури.
- Node 20 LTS (на машині власника — v20.19), менеджер пакетів npm.
- CI — GitHub Actions (вже є), Docker Compose (dev і prod).
- Початкове тестове завдання вимагало серверні шаблони → старий інтерфейс лишається робочим.

## 6. Підходи, які розглядали

| | Опис | Плюси | Мінуси |
|---|---|---|---|
| **A. Окремий SPA + API** (обрано) | React-SPA у `frontend/`, Django віддає API з OpenAPI | Справжня окрема директорія, типобезпечний контракт, гнучкий UX | Більший обсяг: API для всіх екранів |
| Б. Нова «шкіра» для шаблонів | Tailwind + компоненти у шаблонах | Швидко, мало ризику | Не окремий фронт; контракт не потрібен, але й «співпадіння» не гарантується типами |

Власник обрав **A**. Конкретний вибір технологій зроблено мною (власник делегував «як»), див. §7.

## 7. Рішення

### 7.1 Структура репозиторію
```
uptime/                (корінь репозиторію)
  config/ monitors/ accounts/ reports/ ...   ← бекенд без змін у розташуванні
  api/                 ← НОВЕ: Django-застосунок з API (Django Ninja)
  frontend/            ← НОВЕ: SPA (React + TS + Vite)
  docker-compose*.yml, deploy/nginx.conf     ← доповнюються
```
*Моє рішення:* `frontend/` у тому самому репозиторії — один CI, одна збірка, контракт у одному місці.

### 7.2 API
- **Django Ninja**, префікс `/api/v1/`, схеми на Pydantic → автоматична OpenAPI на `/api/v1/openapi.json`.
- *Моє рішення:* Ninja замість DRF — менше шаблонного коду й типи «з коробки»; для нашого обсягу достатньо.
- **Одна валідація на двох:** правила з `MonitorForm` (URL http/https, SSRF-перевірка, коди, заголовки,
  унікальність `(user,url)`, HEAD+текст тощо) виносяться у спільний модуль, який викликають і форма, і API.
  Тести доводять, що обидва шляхи дають однакові помилки.
- Помилки валідації: `422` з тілом `{ "errors": { "<field>": ["..."] }, "message": "..." }` — одним
  форматом для всіх ендпоінтів.
- Пагінація: `?page=&page_size=` (≤100), відповідь `{ items, total, page, pages }`.
- Усі запити обмежені користувачем (як і зараз): чужий id → `404`.

Ендпоінти (орієнтовно):
- Auth: `POST /auth/signup`, `/auth/login`, `/auth/login/2fa`, `/auth/logout`, `GET /auth/me`,
  `POST /auth/confirm`, `/auth/resend`, `/auth/password-reset`, `/auth/password-reset/confirm`;
  `GET/POST /auth/2fa/setup`, `POST /auth/2fa/disable`.
- Monitors: `GET/POST /monitors`, `GET/PATCH/DELETE /monitors/{id}`, `POST /monitors/{id}/check`,
  `GET /monitors/{id}/stats?period=`, `/series?period=`, `/checks`, `/incidents`,
  `GET/POST /monitors/{id}/maintenance`, `DELETE /maintenance/{id}`.
- `GET /dashboard` — список моніторів зі статусом/uptime одним запитом (без N+1).
- Status pages: `GET/POST /status-pages`, `GET/PATCH/DELETE /status-pages/{id}`.
- Reports: `GET/POST /reports`, `GET /reports/{id}/download` (файл — лише власнику).

### 7.3 Авторизація
- **Сесійні cookie + CSRF** (`csrftoken` → заголовок `X-CSRFToken`), один origin: у dev — проксі Vite,
  у проді — nginx віддає і SPA, і `/api/`. **CORS не відкриваємо**, токени в `localStorage` не зберігаємо.
- Логін із 2FA: `/auth/login` повертає `{ "status": "ok" }` або `{ "status": "2fa_required" }` (без входу);
  далі `/auth/login/2fa` приймає код або код відновлення. Правила з поточної реалізації зберігаються
  (≤5 спроб, 5 хв, одноразовість коду, захист від replay).
- Усі «чутливі» повідомлення (скидання пароля, повторний лист) відповідають однаково для існуючих і
  неіснуючих акаунтів — як зараз.

### 7.4 Фронтенд-стек
- **React 18 + TypeScript (strict) + Vite**, React Router, **TanStack Query** (кеш, опитування замість HTMX).
- **Tailwind CSS + shadcn/ui** (компоненти копіюються в проєкт, не «чорна скринька»), іконки lucide.
- Графіки — **Recharts**; форми — react-hook-form + zod, але **повідомлення про помилки беруться з
  відповіді API** (єдине джерело правди).
- Типи й клієнт: `openapi-typescript` + `openapi-fetch` з автогенерації. Скрипт `npm run gen:api`.
- Тести: **Vitest + Testing Library** (компоненти, хуки), **Playwright** (кілька наскрізних сценаріїв
  проти Docker-стека: вхід+2FA, створення монітора, перевірка зараз, вікно обслуговування).

### 7.5 Дизайн-напрямок (обрано мною — власник попросив вибрати самостійно)
«**Спокійний, орієнтований на дані**» — у дусі Linear/Vercel: багато повітря, дрібна типографіка, один
акцент, статуси передають колір.
- **Шрифт:** Inter (системний запасний). **Радіус:** 10 px. **Тіні:** майже відсутні, межі 1 px.
- **Палітра:** нейтральний slate; акцент — індиго `#4F46E5` (світла) / `#818CF8` (темна).
  Статуси семантично: up — зелений, degraded — бурштиновий, down — червоний, maintenance — синій,
  невідомо — сірий. **Колір ніколи не єдиний носій сенсу** (завжди ще й іконка/текст).
- **Навігація:** бічна панель на десктопі (Монітори · Статус-сторінки · Звіти · Безпека), нижня панель
  на мобільному. Перемикач теми (світла/темна/системна), запам'ятовується.
- **Дашборд:** зверху зведення (кількість up/down, відкриті інциденти), нижче — рядки моніторів із
  міні-графіком (sparkline) відповіді за добу, uptime 24 год, бейджем «Down вже N хв» / «Обслуговування».
  Пошук і фільтр за статусом.
- **Сторінка монітора:** заголовок зі статусом і діями («Перевірити зараз», редагувати), вкладки
  «Огляд · Перевірки · Інциденти · Налаштування»; в «Огляді» велика діаграма часу відповіді, картки
  uptime 24 год / 7 / 30 / 90 днів, SSL, вікна обслуговування.
- **Форма монітора:** розбита на розділи (Основне · Перевірка · Публічність) замість 13 полів підряд;
  складні поля (заголовки, тіло, коди, текст) у згорнутому «Розширені»; помилки біля полів + підсумок
  угорі.
- **Стани:** скелети завантаження, порожні стани з поясненням, помилки мережі з кнопкою «Повторити».

Текстовий ескіз дашборда:
```
┌──────────┬────────────────────────────────────────────────────────────┐
│ ◉ Uptime │  Монітори                              [ + Додати ]  ☾    │
│          │  🟢 3 працюють   🔴 1 недоступний   ⚠ 1 інцидент            │
│ Монітори │  [ Пошук…            ]  [ Усі ▾ ]                          │
│ Сторінки │  ─────────────────────────────────────────────────────────│
│ Звіти    │  🟢 Example         ▁▂▁▁▂▁▁▃▁   99.9%   перевірено 12 с тому│
│ Безпека  │  🔴 API (broken)    ▁▁▁▁▁▁▁▁▁    0%     Down вже 42 хв      │
│          │  🛠 Site            ▁▁▂▁         —      Обслуговування      │
└──────────┴────────────────────────────────────────────────────────────┘
```

### 7.6 Публічні статус-сторінки
Лишаються **серверними** (кеш у Redis, SEO, працюють без JS, Atom-стрічка). *Моє рішення:* їх шаблони
перестилізуються під ті самі токени дизайну (кольори, шрифт, радіус, темна тема), щоб бренд був єдиним.

### 7.7 Розгортання й CI
- Dev: `docker compose` додає сервіс `frontend` (Vite dev-сервер із проксі на `web`); альтернативно
  `npm run dev` локально.
- Prod: багатоетапна збірка — Node збирає статику, nginx віддає її та проксює `/api/`, `/status/`,
  `/page/`, `/healthz/`. SPA fallback на `index.html`.
- CI: окреме завдання `frontend` — `npm ci`, `lint`, `tsc --noEmit`, `vitest`, `build`,
  **перевірка синхронності контракту** (`gen:api` → `git diff --exit-code`). Завдання `test` бекенду
  додатково перевіряє, що OpenAPI-схема дає ту саму форму, що закомічена.
- Безпека фронту: CSP без `unsafe-inline` (Vite збирає хешовані файли), `Referrer-Policy`, залежності
  під Dependabot (npm) і `npm audit` у CI.

### 7.8 Етапи
1. **Основа:** застосунок `api`, спільна валідація, OpenAPI, генерація типів, каркас фронту, тема,
   вхід (включно з 2FA, реєстрація, підтвердження email, скидання пароля), дашборд.
2. **Сторінка монітора:** огляд із графіком, перевірки (пагінація, фільтр), інциденти, «Перевірити
   зараз», вікна обслуговування, SSL.
3. **Керування:** форма монітора (створення/редагування), статус-сторінки, звіти (з автооновленням
   статусу), налаштування безпеки (2FA).
4. **Завершення:** публічні сторінки в новому стилі, Docker/nginx, CI, Playwright-сценарії, README.

Після кожного етапу — працюючий стан, тести зелені, коміт.

## 8. Що лишається виконавцю

- Точні схеми відповідей і назви полів (в межах §7.2, єдиний формат помилок обов'язковий).
- Вибір структури папок усередині `frontend/src` і назв компонентів.
- Деталі анімацій, точні відтінки палітри (в межах §7.5 і контрасту AA).
- Чи виносити спільні сервіси в окремий модуль, чи розширювати `monitors/services.py` (головне — без
  дублювання логіки між формою й API).

## 8.1 Дрібні рішення, які я прийняв сам (перевірте)

- `GET /api/v1/auth/csrf` (з `ensure_csrf_cookie`) — SPA викликає його при старті, щоб отримати CSRF-cookie
  до першого POST. Сесійна cookie: `SameSite=Lax`, `HttpOnly`; CSRF-cookie читається JS (потрібно для
  заголовка).
- Менеджер пакетів — npm (без pnpm/yarn), версії закріплені `package-lock.json`.
- Файл звіту завантажується через `fetch` із cookie й віддається як `Blob`, а не прямим посиланням.
- Опитування: дашборд 10 с, сторінка монітора 15 с, статус звіту 3 с — лише коли вкладка видима.
- Мова інтерфейсу — українська; дата/час показуються в часовому поясі браузера, бекенд лишається в UTC.

## 9. Ризики

- **Дрейф валідації** між формою й API → спільний модуль + тест, що порівнює відповіді.
- **Обсяг** (≈ 25 ендпоінтів і ≈ 10 екранів) → строго по етапах, старий інтерфейс як запасний.
- **2FA/сесії в SPA** — найтонше місце безпеки → переносимо вже перевірену логіку, а не переписуємо;
  окремі тести на кожне правило.
- **Опитування** замість push → помірні інтервали (10–15 с, лише коли вкладка видима); SSE — окрема
  майбутня ітерація.
