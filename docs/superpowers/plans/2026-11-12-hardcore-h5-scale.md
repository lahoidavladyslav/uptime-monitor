# Hardcore H5 — scale and backpressure

Spec: `uptime-monitor-hardcore.md` §H5. Branch `hardcore/h5-scale` (stacked on H3).

**Decisions**
- **Engine** (`monitors/async_checks.py`): one `asyncio.run()` per *batch* task, with `httpx.AsyncClient` created and closed inside it (`async with`), so no event loop or connection outlives a task. A global `Semaphore` (concurrency) and **one `Semaphore` per host** (≤ `CHECK_PER_HOST` simultaneous requests to one host, however many monitors point at it). No ORM inside coroutines: the engine takes plain dicts and returns plain tuples; the caller does ONE bulk write. DNS (`blocked_reason`) is blocking, so it runs in a thread, once per unique host per batch. The SSRF guard that `requests` gets from `GuardedAdapter` is re-implemented for httpx as a wrapped `httpcore` network backend (peer address checked right after TCP connect, before any byte is sent: DNS-rebinding safe), pinned by a test because it touches `AsyncHTTPTransport._pool`.
- **Batch task** `check_batch(monitor_ids, region)`: bulk claim (`UPDATE … FROM monitors … RETURNING`, the same atomic "due" test as the single claim, per (monitor, region) clock), configs in one query, engine, then `record_batch`: lock the batch's monitors in id order (no deadlocks), `bulk_create` the results, and run quorum/incident logic ONLY for monitors whose state can change (up with no open incident = zero extra queries). `check_monitor` stays for "check now".
- **Backpressure:** `MonitorRegion.queued_at`. `schedule_checks` marks a (monitor, region) queued with one conditional `UPDATE … RETURNING` and enqueues only the rows it won; a queued monitor is not enqueued again until its batch ran (which clears the flag) or `QUEUED_TTL` (3 min) passed (lost task). "Due" ≠ "checked": a monitor that was overdue for 5 intervals during a stall is checked **once** afterwards, and `last_checked_at = now` makes the next one a full interval away.
- **Metrics** (`/metrics`): queue lengths (Redis `LLEN`), checks in the last minute, p50/p95 response time, number of overdue checks.
- **Load tooling:** `seed_load --monitors N` (spread across `--hosts` host names), `loadtest/fake_target.py` (aiohttp: 50–3000 ms random latency, 5% errors) as an extra container via `docker-compose.load.yml` (with `ALLOW_PRIVATE_TARGETS=1`), `manage.py load_report` prints throughput/latency/overdue. README carries measured numbers and where the bottleneck is.

**Tests pin:** per-host and global concurrency limits are never exceeded and different hosts run in parallel; no ORM access inside the engine; client closed per batch; SSRF at connect (incl. rebinding); body limit; claim atomicity across two batches; steady-state record_batch is O(1) queries per monitor; incidents/quorum/maintenance identical to the single-monitor path; queued flag stops re-enqueueing and clears; stall → exactly one check afterwards; metrics lines.
