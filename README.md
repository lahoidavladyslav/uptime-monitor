# Uptime Monitor

Django 5 · PostgreSQL · Celery + Redis (+ beat) · server-side templates (Bootstrap CDN).

## Запуск

```bash
docker compose up --build
docker compose exec web python manage.py seed_demo   # demo / demo12345
```

Сайт: http://localhost:8000. Листи про інциденти друкуються в лог `worker-notify`
(`EMAIL_BACKEND=console`).

## Листи в dev (реальна пошта)

За замовчуванням листи (підтвердження реєстрації, скидання пароля, сповіщення) **друкуються в логи**
(`docker compose logs web worker-notify`), на справжню пошту нічого не йде. Щоб отримувати їх на пошту,
створіть git-ігнорований файл `.env` у корені (docker compose підхопить його):

```
EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
EMAIL_HOST=smtp.gmail.com
EMAIL_PORT=587
EMAIL_USE_TLS=1
EMAIL_HOST_USER=you@gmail.com
EMAIL_HOST_PASSWORD=<пароль застосунку Google, не основний пароль>
DEFAULT_FROM_EMAIL=you@gmail.com
```
Потім `docker compose up -d` (контейнери перечитають змінні).

## Тести

```bash
pip install -r requirements-dev.txt
pytest                     # потрібен Postgres (DATABASE_URL, дефолт postgres://localhost/uptime)
# або в Docker:
docker compose run --rm web pytest
```

Тести не потребують Redis: `config/settings_test.py` ставить locmem-кеш,
`CELERY_TASK_ALWAYS_EAGER=True` і locmem-email. HTTP мокається через `responses`,
час — через `time-machine`. 178 тестів.

## CI та pre-commit

```bash
pip install -r requirements-dev.txt
pre-commit install          # ruff check --fix, ruff format, trailing whitespace, yaml, ...
```

`.github/workflows/ci.yml` (потрібно, щоб `uptime/` був коренем репозиторію):
- **lint:** `ruff check` + `ruff format --check`;
- **test:** Postgres 16 як service-контейнер, `makemigrations --check --dry-run`
  (модель без міграції ламає збірку), `manage.py check`, `pytest`.
Redis у CI не потрібен — тести використовують locmem і eager Celery.
Версія ruff закріплена (`>=0.17,<0.18`) і збігається з `rev` у pre-commit, щоб локально
й у CI правила не розходились.

## Ключові рішення та trade-offs

**N+1 на дашборді.** Один запит: `Subquery` для статусу останньої перевірки й
відкритого інциденту + `Count(filter=Q(...))` для uptime 24 год. Тест
`test_dashboard_has_constant_query_count` фіксує, що кількість запитів не росте з
кількістю моніторів.

**Хто пора перевіряти — у БД.** `schedule_checks` фільтрує через
`F('last_checked_at') + F('interval_seconds') * interval '1s' <= now()`.
`DUE_SLACK = 10 с`: `last_checked_at` — це *початок* перевірки, а beat тікає раз на
хвилину; без запасу 60-секундний монітор «дрейфував» би до перевірки раз на 2 хв.

**Дублі `check_monitor` і блокування.** Три короткі фази:
1. *claim* — один умовний `UPDATE monitors SET last_checked_at=now WHERE id=… AND <пора>`.
   Postgres серіалізує конкурентні апдейти рядка й перераховує `WHERE`, тож із N дублів
   рівно один бачить монітор «простроченим» і виграє; решта виходять (`"skipped"`).
2. *HTTP* — **поза транзакцією**: ні з'єднання з БД, ні рядок не тримаються ≤10 с.
3. *запис* — коротка транзакція з `select_for_update` на моніторі: серіалізує
   відкриття/закриття інциденту й запис результату.

Trade-off: at-most-once на інтервал. Якщо воркер впаде між claim і записом, перевірка
цього інтервалу втрачається (наступна піде за розкладом) — це свідомо замість
довгого локу. «Перевірити зараз» (`force=True`) пропускає умову «пора»; збіг двох
ручних запусків безпечний завдяки локу на фазі запису. Якщо монітор видалили під час
запиту — задача чесно виходить. Чому не Redis-lock: окрема система з TTL, яку треба
узгоджувати з БД; тут стан і так у Postgres.

**Інциденти.** Open/close — всередині того ж локу; частковий `UniqueConstraint`
(`resolved_at IS NULL`) — страховка на рівні БД. Нотифікація йде через
`transaction.on_commit` і передається лише `incident_id`. Email — з
`autoretry_for=(SMTPException, OSError)`, `retry_backoff`, `max_retries=3`.

**Статистика.** Тільки `aggregate`/`Count(filter)`/`Avg`/`Min`/`Max`; без даних —
«немає даних», а не ділення на 0. Смужка 7 днів — один запит
(`TruncDate` + `values` + `annotate`); дні рахуються в UTC.

**Публічна сторінка.** Кешується весь HTML (60 с). Інвалідація — сигнали
`post_save/post_delete` на `Monitor`, двічі: одразу і ще раз в `on_commit` (щоб
конкурентний запит не повернув у кеш старий стан). Збій Redis при інвалідації не
ламає збереження монітора. Обмеження: `queryset.update()` сигналів не викликає —
тому `check_monitor` оновлює `last_checked_at` саме так (інакше кожна перевірка
скидала б кеш), а статус на сторінці може відставати до 60 с. URL і тексти
помилок у шаблон не передаються взагалі.

**Звіти.** Дві згруповані SQL-запити (checks і incidents по `monitor_id`), у Python
лише зливаються рядки моніторів. Простій інциденту обрізається межами періоду
(`Greatest/Least`), відкритий інцидент рахується до «зараз». Статус
`pending → processing` захоплюється атомарним `UPDATE ... WHERE status='pending'`,
тому повторна доставка задачі нічого не робить. Завантаження — через view з
перевіркою власника (`FileResponse`), `/media/` напряму не віддається.

**Очистка.** Сирі перевірки видаляються **цілими добовими партиціями** (`DROP`) задачею `manage_partitions`
(див. Hardcore → H3); rollup-и живуть рік.

**SSRF.** `monitors/security.py`: хост резолвиться, і якщо *будь-яка* адреса не
`is_global` (loopback, RFC1918, link-local/cloud-metadata `169.254.169.254`, CGNAT,
IPv6 ULA, IPv4-mapped IPv6) — URL відхиляється у формі **і повторно перед кожною
перевіркою** (DNS міг змінитись після збереження). Редіректи не відстежуються, тож
обхід через 302 неможливий. Нерезолвний хост не блокується — це просто «down».
`ALLOW_PRIVATE_TARGETS=1` вимикає захист (для локальної розробки). Залишковий ризик:
вузьке вікно DNS-rebinding між нашим резолвом і з'єднанням `requests`; повністю
закрити можна лише підключенням до вже перевіреної IP.

**Rate-limit.** «Перевірити зараз» — не частіше разу на 10 с на монітор (атомарний
`cache.add`; при недоступному кеші дозволяємо, а не 500). Звіти — не більше 3
одночасно в черзі на користувача.

**Графік.** Розмір набору точок обмежений незалежно від кількості перевірок: 24 год —
сирі точки (≤1440), 7 днів — погодинні бакети, агреговані в SQL (≤168). Невдала
перевірка без часу відповіді дає розрив лінії, падіння позначені червоним хрестиком.
Дані передаються через `json_script` (безпечне екранування), без окремого API.

**HTMX-дашборд.** Таблиця опитується раз на 10 с лише поки вкладка видима; сервер на
HTMX-запит віддає тільки фрагмент таблиці (той самий запит, без N+1). Якщо сесія
спливла, у відповідь іде `204 + HX-Redirect` на логін, а не сторінка входу всередині
таблиці. Мінус: опитування, а не push (SSE/WebSocket дали б менше навантаження).

**DNS-rebinding.** Попередня перевірка резолвить хост, але з'єднання резолвить ще раз —
ворожий DNS міг би відповісти «публічною» адресою першого разу і `127.0.0.1` другого.
Тому `monitors/http_client.py` підміняє клас з'єднання urllib3 і перевіряє **адресу
реально підключеного сокета** (`getpeername()`), незалежно від того, що казав DNS.
Перевірено на справжньому TCP-сервері в тестах і в Docker (`redis`, `db`, `web`,
`169.254.169.254` — усе блокується).

**Акаунти** (`accounts/`):
- *Підтвердження email:* новий акаунт `is_active=False`, лист із підписаним
  (`TimestampSigner`, 3 дні) посиланням; повторне надсилання не розкриває, чи існує email.
- *Скидання пароля:* стандартні токени Django; для невідомого email відповідь та сама.
- *2FA (TOTP):* QR/ключ → підтвердження кодом → 8 кодів відновлення (показуються один
  раз, у БД лише SHA-256). Після правильного пароля користувач **ще не залогінений**
  (`pre_2fa` у сесії, 5 хв, ≤5 спроб); код одноразовий (захист від replay через
  `last_used_step`); `next` перевіряється на open-redirect. Вимкнення — за паролем.
  Секрет TOTP шифрується Fernet-ключем поза БД (див. «Безпека акаунтів» нижче).
  Скидання пароля не вимикає 2FA.
- *Залежності:* Dependabot (pip, actions, docker) і `pip-audit` у CI.

**Розширені перевірки.** На моніторі можна задати метод (GET/HEAD/POST), заголовки,
тіло (POST), очікувані коди (`200,204,300-399`) та текст, що має бути у відповіді.
Тіло читається лише коли задано текст, не більше 1 МБ і не довше за загальний
таймаут (захист від «крапельних» серверів). Заголовки `Host`, `Content-Length`,
`Transfer-Encoding`, `Connection` заборонені. Відповідь 200 з неправильним текстом —
це **down**, з окремим повідомленням. Усе, що стосується SSRF, діє й тут.

**SSL-сертифікат.** Щодобова задача (04:00 UTC) читає `notAfter` через guarded-сокет,
шле один лист на кожен поріг (14 днів → 3 дні → прострочений) — `ssl_alerted_level`
захоплюється умовним `UPDATE`, тому два воркери не продублюють лист; після
продовження сертифіката стан скидається. Невалідний/прострочений сертифікат
показується на сторінці монітора.

**Вікна обслуговування.** У вікні перевірки **не виконуються** (ні за розкладом, ні
«Перевірити зараз»), тож цей час не рахується простоєм, а на публічній сторінці
показується «Планові роботи». Обмеження: інцидент, відкритий до початку вікна,
залишається відкритим, поки перевірка не відновиться після вікна.

**Публічні сторінки** (`monitors/public.py`):
- *Один монітор* `/status/<slug>/` і *група* `/page/<slug>/` (модель `StatusPage`, M2M до
  моніторів власника — форма пропонує лише свої). Є назва, опис, логотип (лише http/https),
  загальний банер (працює / частковий збій / збій / планові роботи), смужка 7 днів і
  історія інцидентів за 30 днів **без текстів помилок і URL**.
- *Запити:* незалежно від кількості моніторів — константа (`daily_bars`, `uptime_by_monitor`
  групують по `monitor_id` в одному запиті); тест фіксує стелю.
- *Кеш:* 60 с, інвалідація сигналами при збереженні/видаленні монітора, вікна
  обслуговування, сторінки та зміні складу групи (двічі: одразу і в `on_commit`).
  Видалення монітора інвалідує й групи, до яких він входив (`pre_delete`, поки зв'язки ще є).
- *Підписка:* Atom-стрічка `/status/<slug>/feed/` і `/page/<slug>/feed/`. Для інциденту
  два записи (початок і відновлення) з різними `guid`, щоб читалка показала новий запис
  про відновлення. `Cache-Control: max-age=60`. Email-підписки не робив: це double-opt-in,
  токени відписки й антиспам — окремий обсяг.

## Експлуатація

**Production-стек** (`docker-compose.prod.yml`, `Dockerfile.prod`, `deploy/nginx.conf`):

```bash
cp .env.example .env.prod      # заповнити SECRET_KEY, ALLOWED_HOSTS, паролі, SMTP
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

- gunicorn за nginx; статика збирається при збірці образу й віддається WhiteNoise
  (S3 не потрібен: медіа — лише звіти, які віддаються через view з перевіркою власника).
- `DJANGO_ENV=production` вмикає fail-fast: без `SECRET_KEY` і `ALLOWED_HOSTS` застосунок
  **не стартує**; `DEBUG` примусово вимкнений; Secure-cookies, HSTS, SSL-redirect
  (`/healthz/` виключений, бо проби приходять по HTTP). `manage.py check --deploy` без
  попереджень (перевіряється тестом). HSTS-preload — лише за явним `HSTS_PRELOAD=1`.
- Контейнер працює від непривілейованого користувача; міграції — окремий one-shot сервіс,
  від якого залежать усі інші. TLS термінується **перед** nginx (балансувальник/Caddy),
  який має виставляти `X-Forwarded-Proto`.
- nginx: `limit_req` на `/login|signup|password-reset|confirm` (429 після ліміту).
- Брокер і кеш Celery — окремі Redis-бази (`REDIS_URL` / `CACHE_REDIS_URL`).

**Окремі черги й воркери.** `checks` (цикл перевірок, SSL, rollup), `notifications`
(листи), `reports` (CSV, `-c 1 -O fair`, `prefetch=1`). Довгий звіт ніколи не стоїть
перед перевіркою або листом. Перевірено вживу: кожне завдання потрапляє у свій воркер.

**Спостережуваність:**
- `GET /healthz/` — 200, якщо веб-процес бачить БД і кеш (інакше 503). Поле `checks: stale`
  показує, що фоновий конвеєр (beat → worker) мовчить, але **код відповіді не змінює**:
  перезапуск web не оживить мертвий worker.
- `GET /metrics/` — Prometheus-формат, **вимкнений, поки не задано `METRICS_TOKEN`**,
  далі Bearer-авторизація (порівняння за постійний час). Метрики: монітори за станом,
  відкриті інциденти, перевірки за 5 хв, статуси звітів, SSL ≤14 днів і
  `uptime_scheduler_lag_seconds` — вік найбільш простроченої перевірки: зростає, коли
  зупинилися beat або воркери (основний алерт). Кількість запитів не залежить від числа моніторів.
- Sentry — лише якщо задано `SENTRY_DSN` (`send_default_pii=False`).
- **Структуровані логи.** У production — один JSON-рядок на подію (`LOG_FORMAT=json|plain`
  перевизначає), у dev — звичайний текст. Кожен рядок має `request_id` (з заголовка
  `X-Request-ID`, якщо він безпечний, інакше генерується; повертається у відповіді) або
  `task_id` для Celery. Access-лог пише **шаблон маршруту** (`confirm/<str:token>/`), а не
  сирий шлях — токени підтвердження/скидання/відписки лежать в URL; пише `user_id`, але
  ніколи email, query-рядок чи тіло. Стандартний `django.request` (він друкує сирі шляхи
  для кожного 4xx) приглушений до ERROR, gunicorn access-log вимкнений. `/healthz/` не логується.
  IP клієнта береться з `X-Real-IP` лише в production (його виставляє наш nginx;
  `TRUST_PROXY_HEADERS`). Якщо перед nginx є ще один балансувальник — налаштуйте real_ip.
- **Журнал входів.** `LoginEvent` пишеться з Django-сигналів автентифікації (веб і API
  користуються одним `login()`), плюс невдалі коди 2FA та блокування. Видно власнику на
  «Безпека акаунта» і в `GET /api/v1/account/login-events`; зберігається 90 днів.
  Спроби з **невідомим логіном у БД не пишуться** (шум від ботів, а в полі логіну люди
  часто вставляють пароль) — лише в лог, без імені.

**Безпека акаунтів.**
- **TOTP-секрети шифруються в БД** (Fernet, випадковий IV на кожен запис; ключ у
  `TOTP_ENCRYPTION_KEYS` поза базою). Дамп БД сам по собі більше не дає генерувати коди.
  У production без ключа застосунок не стартує, неправильний формат теж ловиться на старті.
  Ротація: додати новий ключ *першим* (`new,old`), задеплоїти, пізніше прибрати старий. Втрата
  ключа = користувачі налаштовують 2FA заново (кошти відновлення — коди відновлення). У dev
  ключ виводиться з `SECRET_KEY`. Міграція `0003` шифрує наявні рядки (ідемпотентна).
  Обмеження: ключ і код живуть в одному середовищі; для вищого рівня — KMS/секрет-менеджер.
- **Реєстрація не розкриває, чи є email у системі.** Нова адреса, непідтверджений акаунт і
  активний акаунт отримують однакову відповідь; у другому випадку піде повторний лист
  підтвердження, у третьому — лист власнику «у вас уже є акаунт» з посиланням на відновлення.
  Логін, що вже зайнятий, **досі повідомляється** (це неминуче, поки логін унікальний і
  показується); нагромаджується лише nginx-лімітом.
- Swagger і `openapi.json` у production **закриті** (`API_DOCS=1` вмикає). Контракт для
  фронтенду береться з файлу в репозиторії, а не з живого сервера.

**Email-підписки на статус-сторінки.** Публічні сторінки (групова й окремого монітора) мають
посилання «Сповіщення на email» → окрема *некешована* форма (в кешованій сторінці не може бути
CSRF-токена). Double opt-in: лист із посиланням (3 дні), без підтвердження листів немає, а
непідтверджені рядки чистяться щодоби. Відповідь на форму однакова для нової, очікуючої й уже
підтвердженої адреси (не можна дізнатися, хто підписаний); повторний лист — не частіше ніж раз
на 10 хв на адресу, 10 запитів/год на IP, не більше 5000 підписників на сторінку. Відписка —
посилання в кожному листі + `List-Unsubscribe` / `List-Unsubscribe-Post` (RFC 8058, one-click).
GET-посилання відписки лише показує кнопку: поштові сканери відкривають лінки й не повинні
відписувати людей. Листи містять **лише публічні дані** (публічна назва, час, тривалість) — без
URL моніторингу й тексту помилки. Один лист на адресу, навіть якщо вона підписана і на групу,
і на монітор. Посилання в листах будуються від `SITE_URL`.

Детальніше про rollup і його підводні камені — у розділі **Hardcore → H2** нижче.

## Frontend (SPA, `frontend/`)

React 18 + TypeScript + Vite + Tailwind; говорить з `/api/v1/` сесійними cookie + CSRF (один origin,
без CORS). Старий Django-інтерфейс на `:8000` лишається робочим.

```bash
docker compose up -d --build        # frontend на http://localhost:5173 (проксі /api -> web)
# або локально:
cd frontend && npm ci && npm run dev    # потрібен бекенд на :8000
npm test -- --run                        # Vitest + Testing Library + MSW
npm run lint && npm run typecheck && npm run build
```

**Контракт не може розійтися.** Типи `src/api/schema.d.ts` генеруються з `api/openapi.json`
(`npm run gen:api`). Змінили API → `python manage.py export_openapi` → `npm run gen:api` → коміт обох файлів.
CI падає, якщо знімок або типи застарілі (`export_openapi --check`, `git diff --exit-code`).

**Production:** задайте `FRONTEND_URL` (див. `.env.example`): листи підтвердження й скидання пароля з API
ведуть на SPA. nginx обмежує перебір на `/login|signup|…` і на `/api/v1/auth/(login|signup|…)`.

Етап 1: вхід (з 2FA), реєстрація, підтвердження email, скидання пароля, дашборд.
Етап 2: **сторінка монітора** (`/monitors/:id`, вкладки в `?tab=`): картки uptime 24 год/7/30/90 днів,
графік часу відповіді (Recharts, підвантажується лише тут; збої = розрив лінії + червоні точки),
статистика за період, SSL, вікна обслуговування (створення/видалення; час вводиться локальний, на сервер
йде UTC), перевірки (пагінація, фільтр «лише падіння» на сервері), інциденти, «Перевірити зараз»
(клієнтська пауза 3 с + серверний cooldown → 429, обслуговування → 409). Чужий або неіснуючий id → 404.
Решта екранів (форма монітора, статус-сторінки, звіти, безпека) — етапи 3–4, поки що заглушки.
Версії vite/vitest/msw закріплені під Node 20 (новіші мажорні вимагають Node ≥ 22.12).

## Відомі обмеження / що б робив далі

- Підписники не мають особистого кабінету: керування лише через посилання в листах; власник не бачить їх список (лише через адмінку).

- `allow_redirects=False`: 3xx вважається «up» за ТЗ, редірект не відстежується.

## Hardcore

### H2. Погодинні rollup-таблиці (`hardcore/h2-rollups`)

**Що зроблено.** `CheckRollupHourly` (`monitor × година UTC`: `checks_total`, `checks_up`,
`sum_response_ms`, `response_count`, `min/max_response_ms`, unique `(monitor, hour)`). Задача
`build_rollups` кожні 5 хв перераховує **попередню й поточну** годину **одним**
`INSERT … SELECT … GROUP BY … ON CONFLICT DO UPDATE` (дані не залишають БД). Сирі перевірки живуть
**7 днів**, rollup — **365**. Із rollup читають: статистика за 7 днів і графік, публічна сторінка
(uptime 7 днів і смужка по днях), звіти (тепер можна й за періоди, чиї сирі рядки вже видалені),
uptime за 30/90 днів. 24-годинні видки лишились на сирій таблиці (≤1440 рядків на монітор, індекс).
`backfill_rollups --from --to` перебудовує **перезаписом**, по одному `INSERT … SELECT` на добу.

**Підводні камені й як їх обійдено**
- *Запізнілий результат.* Рядок належить годині за `checked_at`, а не за часом запису; перераховуються
  дві години, тож результат, що доїхав у наступну годину, оновить свою (тест із «завислим воркером»).
  Межа: пізніше ніж на ~годину — лише `backfill_rollups`.
- *`avg`.* Зберігаються `sum` і `count`. Причому `count` — це `response_count` (перевірки з часом
  відповіді), а **не** `checks_total`: збійні перевірки часу не мають. Тест: 9×100 мс і 1×1000 мс дають
  190, а не 550 (середнє середніх).
- *Rollup == raw.* Один шлях читання (`monitors/rollups.py`): для вікна `[start, end)` годин `< T`
  відповідає rollup, решта — сирі рядки, `T = початок_години(now) − 1 год`. Чому не «сирі лише для
  поточної години»: година H−1 остаточна лише після першого запуску **після** межі; читаючи її з сирих
  до двох годин, ми ніколи не показуємо напівготовий рядок (тест: rollup побудований о 12:58, о 13:02
  користувач усе одно бачить обидві перевірки; зміна межі на `floor_hour(now)` цей тест ламає).
  Вікно N днів = `[початок_години(now) − N·24 год, now)` на обох шляхах, тому вони порівнювані; тест
  звіряє rollup із сирим SQL для статистики, uptime, смужок, графіка й звіту у три моменти «зараз»
  (одразу після півночі, вдень, о 23:59), а також що старі години справді беруться з rollup (видалили
  сирі — число те саме; підмінили рядок rollup — число змінилось).
- *Часові пояси.* Усе в UTC явно (`AT TIME ZONE 'UTC'`, `TruncDate/TruncHour(tzinfo=UTC)`), а не через
  `TIME_ZONE`; тест із `Asia/Kolkata` (+05:30) — година не зсувається.
- *Очищення не має ламати rollup.* Межа очищення вирівняна по годині: година або повністю є, або повністю
  зникла, бо «напівпрожите» рядки перебудували б у неправильний rollup. `backfill` пише лише години, для
  яких ще є сирі рядки, тому не стирає старе (тест).
- *Запити.* Деталь монітора рахує uptime 7/30/90 одним rollup- і одним raw-запитом (умовні `Sum(filter=…)`),
  а не двома на кожне вікно.

**Свідомо спрощено.** Вікно «7 днів» — це 168 повних годин + поточна (а не рівно 7×24 год від «зараз»).
Міграція `0006` перейменовує `HourlyStat` без втрати даних і заповнює `min/max` з наявних сирих рядків
одним `UPDATE`; для великих таблиць це одноразовий скан. Після деплою запустіть
`manage.py backfill_rollups` **до** першого нічного очищення (воно тепер лишає лише 7 днів сирих даних).

### H1. Webhooks із transactional outbox (`hardcore/h1-webhooks`)

**Що зроблено.** `WebhookEndpoint` (монітор, url, `secret` — шифрований Fernet-ом у БД, `is_active`) і
`OutboxEvent` (`event_type`, `payload`, `created_at`, `processed_at`, `attempts`, `next_attempt_at`,
`last_error` + `endpoint`, `event_id`, `status = pending|delivered|dead`). Інцидент і рядки outbox
створюються **в одній транзакції** (`update_incident` виконується всередині `check_monitor`): або є обидва,
або жодного (тест із відкотом). Періодична `dispatch_outbox` (кожні 15 с, плюс «поштовх» після коміту)
доставляє. Сторінка `/monitors/{id}/webhooks/`: ендпоінти (секрет видно власнику), журнал доставок,
«Повторити» для `dead`.

**Протокол.** `POST`, тіло — JSON, заголовки `X-Signature: sha256=<hex>` (HMAC-SHA256 від тіла з секретом),
`X-Event-Id`, `X-Timestamp`, `X-Event-Type`. Backoff 1, 2, 4, 8… хв ±25% jitter, **8 спроб**, далі `dead`.
Редіректи не слідуємо, відповідь не 2xx = невдача. Приклад перевірки на боці одержувача —
`monitors.webhooks.verify_signature` (`hmac.compare_digest`).

**Підводні камені й як їх обійдено**
- *Два воркери не беруть одну подію.* Claim — коротка транзакція `SELECT … FOR UPDATE SKIP LOCKED`, після
  якої виставляється **lease** (`next_attempt_at = now+2 хв`, `attempts+1`). HTTP-запит іде **поза**
  транзакцією, тому жоден рядок не заблокований на час повільної відповіді. Тести: два потоки через
  бар'єр не перетинаються; рядок, заблокований третьою транзакцією, не блокує claim (без `skip_locked`
  цей тест падає — перевірено мутацією).
- *Повільний/мертвий ендпоінт не блокує решту.* `dispatch_outbox` лише claim-ить і ставить окрему
  Celery-задачу на кожну подію; тайм-аут запиту 3+5 с. Тест: мертвий ендпоінт із трьома подіями й
  здоровий — здоровий доставлений за той самий прогін.
- *Підпис від точних байтів.* Єдина `serialise()` (`sort_keys`, компактні роздільники) повертає `bytes`;
  ці самі байти і підписуються, і відправляються (`data=body`). Тест беремо з **перехопленого запиту**,
  а не з dict.
- *Порівняння підписів* — `hmac.compare_digest` (тест перевіряє, що саме він викликається; змінене тіло,
  чужий секрет, відсутня схема, `sha1=` — усе відхиляється).
- *At-least-once.* Воркер може впасти після відповіді одержувача, але до запису результату, тож
  дублі можливі; для цього є стабільний `X-Event-Id`. Упавший посеред доставки воркер нічого не губить:
  lease спливає, подію беруть знову; якщо подія вичерпала спроби «на падіннях», сторож переводить її в `dead`.
- *SSRF.* URL перевіряється при збереженні **після резолву DNS** (ім'я, що веде на `10.x`, `127.x`,
  `169.254.169.254`, `::1`, `::ffff:10.x`, відхиляється) **і на кожну спробу доставки** плюс на рівні
  з'єднання (`guarded_session`, захист від DNS rebinding: тест підміняє резолв після створення —
  запит навіть не виходить).
- *Ручний «Повторити» не перетирається* запізнілим результатом попередньої спроби: запис результату —
  умовний `UPDATE … WHERE status='pending'`.

**Свідомо спрощено.** Подія створюється на кожен активний ендпоінт на момент переходу стану (вимкнений
пізніше ендпоінт просто не отримує вже поставлені події). Немає per-endpoint rate limit і circuit
breaker: мертвий ендпоінт «з'їдає» лише свої 8 спроб. Підпис — лише від тіла, як у ТЗ; захист від replay
робить одержувач за `X-Event-Id`. Старі `delivered/dead` події чистяться через 30 днів.

### H4. Перевірка з кількох регіонів і кворум (`hardcore/h4-regions`)

**Що зроблено.** `CheckResult.region`; воркери з `CHECK_REGION=eu|us|asia` слухають власну чергу
`checks.<region>` (у `docker-compose*.yml` — три сервіси `worker-eu/us/asia`; окремий `worker` обслуговує
планувальник, SSL, rollup-и). `schedule_checks` і «Перевірити зараз» розсилають по задачі в **кожен** регіон
(`CHECK_REGIONS`). Статус по регіонах видно на сторінці монітора (Django, `GET /api/v1/monitors/{id}` →
`regions[]`, картка «Регіони» у SPA).

**Кворум** (`monitors/regions.py::decide`) — чиста функція від «останнього результату кожного регіону»:
- голос регіону — його останній результат, якщо він у межах **2 хв** від оброблюваного;
- учасники — регіони, що відповідали протягом `max(5 хв, 2×інтервал)`; **мовчазні виключаються** (не «up»
  і не «down») і показуються в UI як «немає даних»; регіон, що ще не встиг відповісти, поки монітор
  «молодий», лишається учасником, тож перший раунд нового монітора не вирішує одна швидка відповідь;
- `need = учасники // 2 + 1` (2 з 3, 2 з 2, 1 з 1); `down ≥ need` → інцидент, `up ≥ need` → закриття,
  інакше нічого не змінюється. Закриття теж за кворумом — це і є антифлап.

**Підводні камені й як їх обійдено**
- *Порядок і гонка.* Рішення рахується після кожного запису **під блокуванням рядка монітора**
  (`select_for_update`) і залежить лише від набору останніх результатів, а не від порядку приходу;
  тести перебирають усі 6 перестановок `(eu↓, us↓, asia↑)` — завжди рівно один інцидент — і `(↓,↑,↑)` —
  жодного. Один відкритий інцидент додатково гарантує часткове `UniqueConstraint`.
- *Тест на гонку без везіння.* Два потоки доходять до `decide` лише після того, як **обидва** вже записали
  результат (бар'єр усередині транзакції). Без блокування рядка кожен бачив би тільки свій результат
  (чужий ще не закомічений), обидва сказали б «кворуму немає» — і збій лишився б непоміченим (lost update).
  Перевірено мутацією: без `select_for_update` цей тест падає, з ним — рівно один інцидент і один webhook.
- *Мовчазний регіон.* Його старий «up» не може перекричати два свіжі «down», а його мовчання не вважається
  «down». Єдиний живий регіон вирішує сам (`1 з 1`); два живі з розбіжністю (`up` + `down`) — без рішення.
- *Клейм по регіонах.* Атомарний `UPDATE` годинника `(монітор, регіон)` (`MonitorRegion`): дубль задачі
  **того ж** регіону пропускається, інші регіони працюють незалежно. `Monitor.last_checked_at` лишився
  годинником планувальника й дашборда.
- Індекс `(monitor, region, checked_at)` обслуговує `DISTINCT ON (region)` — «останній результат кожного регіону».

**Свідомо спрощено.** Вікно голосів і поріг мовчання — константи (2 хв / 5 хв), не налаштування. Регіони в цій
реалізації — це окремі воркери з власними чергами в одній мережі compose; справжня гео-розподіленість
потребує розгортання воркерів у різних мережах (код при цьому не змінюється). Якщо воркер регіону лежить,
його черга накопичує задачі; після відновлення виконається лише одна (клейм відсікає решту), а контроль
зростання черги — тема H5 (backpressure).

### H6. Maintenance windows і дедуплікація алертів (`hardcore/h6-maintenance`)

**Зміна поведінки.** Раніше вікно *зупиняло* перевірки. Тепер, як у завданні, перевірки **тривають і
зберігаються** (з прапорцем `in_maintenance`), але в межах вікна не відкривають інцидентів і не впливають
на uptime/середній час відповіді.

**Що зроблено.** `MaintenanceWindow`: `monitor` або «усі монітори користувача» (`monitor = NULL`), `rrule` +
`timezone` (IANA). Рядок з `rrule` — **шаблон**; періодична `expand_maintenance` (і збереження) матеріалізує
конкретні входження на місяць уперед; усе, що питає «чи зараз обслуговування» (SQL-`Exists`, дашборд,
публічна сторінка, кворум, uptime), дивиться лише на конкретні рядки — повторення живе в одному місці. Інцидент,
відкритий до вікна, **не закривається штучно**: він лишається відкритим і позначається `during_maintenance`
(закривається звичайно, коли сайт справді відновився). **Flapping:** більше 4 змін стану (відкриття+закриття
інцидентів) за 15 хв → один лист/webhook `monitor.flapping` «нестабільний» замість п'ятого алерту, далі листи,
листи підписникам і webhook-и по інцидентах **вимкнені**, історія інцидентів пишеться як завжди; 15 тихих
хвилин → один лист/webhook «стабілізувався» зі станом, у якому монітор осів.

**Підводні камені й як їх обійдено**
- *rrule + пояси + DST.* Повторення рахуються як **локальний настінний час** у поясі вікна (naive `RRULE`
  по локальних датах, кожне входження локалізується `zoneinfo`), а не як фіксований зсув UTC: «щонеділі
  02:00–03:00 Europe/Kyiv» — це 00:00 UTC узимку й 23:00 UTC (у суботу) влітку. Тест перевіряє справжні
  переводи 2026 року: 29.03 (03:00 не існує → беремо зсув *до* переходу, вікно все одно 1 год) і 25.10
  (03:00 буває двічі → перше). Вікно, що повністю потрапляє в «дірку» (03:30–04:30), не стає порожнім: падаємо
  на абсолютну тривалість. Мутація «усе в UTC» валить чотири тести.
- *Небезпечні правила.* Лише `DAILY|WEEKLY|MONTHLY`, без `BYHOUR/BYMINUTE/BYSECOND/DTSTART`, `INTERVAL ≥ 1`,
  `COUNT ≤ 1000`; `FREQ=SECONDLY` відхиляється з помилкою поля. Невідомий пояс — теж.
- *Uptime: віднімається час вікна, а не кількість перевірок.* Можна було б відняти «довжина вікна / інтервал =
  очікувана кількість перевірок», але це ламається, щойно інтервал змінили, частину перевірок втратили або
  (H4) регіонів стало три і семплів утричі більше. Тому виключаються **самі семпли, чий час потрапив у
  вікно** (прапорець ставиться у момент запису): оскільки семпли рівномірні в часі, це рівносильно відніманню
  часу вікна зі знаменника, а не залежить від ритму перевірок. Тест: у годинному вікні лише 30 семплів
  (замість 60 «очікуваних») — виключаються рівно ці 30, і uptime лишається 100%. Простій *інциденту* у звітах
  зменшується на **перетин за часом** з вікнами (перекриті вікна зливаються, не рахуються двічі).
- *Узгодженість із rollup (H2).* SQL побудови rollup і всі «сирі хвости» (24 год, добові смужки, графік) мають
  `NOT in_maintenance`; тест порівнює 7-денні числа з rollup та з сирих рядків, коли частина вікон давно
  в rollup, а одне ще триває.

**Свідомо спрощено.** Прапорець `in_maintenance` — знімок на момент запису: якщо вікно потім змінити або
видалити, старі семпли не перераховуються. Графік 24 год показує всі семпли (чесний сирий вигляд). Вікна
редагуються видаленням і створенням заново. Для SPA форма створення вікна поки не має полів повторення (API
їх уже приймає).

### H3. Партиціювання `CheckResult` (`hardcore/h3-partitioning`)

**Що зроблено.** `monitors_checkresult` — `PARTITION BY RANGE (checked_at)`, по партиції на добу (UTC,
`monitors_checkresult_pYYYYMMDD`) + `…_default`. Міграція `0010` (`SeparateDatabaseAndState`): `RunSQL` з
**робочим `reverse_sql`** (перейменувати стару → створити партиційовану + партиції на всі дні наявних даних і
3 дні вперед → скопіювати рядки зі збереженням `id` → індекси/FK → видалити стару; зворотний напрям — дзеркально
до звичайної таблиці з identity; тест проганяє `migrate … 0009` і назад із даними). Задача `manage_partitions`
(щогодини) створює партиції на 3 дні вперед, прибирає зайве й **дропає** партиції за межею retention (7 днів) —
`cleanup_old_checks` із батчевим `DELETE` більше немає.

**Primary key.** Postgres вимагає ключ партиціювання в кожному унікальному ключі, тому в БД PK — `(id, checked_at)`.
Обрав **`CompositePrimaryKey("id", "checked_at")`** (Django 5.2), а не unmanaged-модель із «фальшивим» одноколонковим pk:
`pk`, `save()`, `delete()`, `filter(pk=…)`, `bulk_create` лишаються робочими, а модель каже правду про схему.
`id` — звичайний `BigIntegerField` із `db_default=nextval('monitors_checkresult_id_seq')`: Django не пише його в
`INSERT` і читає назад через `RETURNING` (перевірено спайком: create/bulk_create/save/delete). Ціна: `CheckResult`
не можна зареєструвати в адмінці (вона не вміє складені ключі; для мільйонів сирих рядків вона й так даремна).

**Чому `DROP` партиції, а не батчевий `DELETE`** (виміряно, Postgres 16, 1 000 000 рядків за добу, 2 індекси):

| | батчевий `DELETE` (по 5000) | `DROP` партиції |
|---|---|---|
| час | **9,2 с** | **14 мс** |
| WAL | **113 МБ** | **~60 кБ** |
| мертві рядки після | **1 000 000** (чекають VACUUM) | 0 |
| місце на диску після | 142 МБ **не повернулось** (таблиця й індекси роздуті) | **повернулось одразу** |

`DELETE` пише по записові в WAL і по надгробку на кожен рядок та запис індексів, лишає bloat, який треба
вичистити `VACUUM`-ом, і навантажує реплікацію; `DROP` — це операція з каталогом.

**Partition pruning** (`EXPLAIN (ANALYZE)` на dev-БД; запит за добу одного монітора чіпає лише одну партицію і
її індекс, `default` та інші дні не зачеплені):

```
Aggregate (actual rows=1 loops=1)
  ->  Index Scan using monitors_checkresult_p20261112_monitor_id_checked_at_idx
        on monitors_checkresult_p20261112 monitors_checkresult (actual rows=63 loops=1)
        Index Cond: ((monitor_id = 2) AND (checked_at >= '2026-11-12 00:00:00+00') AND (checked_at < '2026-11-13 00:00:00+00'))
```
У тестах pruning перевіряється по `EXPLAIN`: партиції поза діапазоном у плані **відсутні**.

**Підводні камені й як їх обійдено**
- *Рядок за день без партиції.* Він не падає з помилкою, а потрапляє в **default-партицію**. Вона має бути
  порожньою: `/metrics` → `uptime_checkresult_default_partition_rows`, а `manage_partitions` пише `WARNING`,
  якщо там щось лишилось. Наступний запуск **усиновлює** такі рядки: `CREATE TABLE … PARTITION OF` у цей момент
  впав би («constraint of default partition would be violated»), тому будується окрема таблиця
  (`LIKE … INCLUDING INDEXES`), рядки переносяться `DELETE … RETURNING → INSERT`, потім `ATTACH PARTITION`
  (CHECK, рівний діапазону, дозволяє `ATTACH` не перевіряти рядки заново). Усиновлюються лише дні в межах
  `retention … сьогодні+3`: бездумна дата (2099 чи 2001) **не створює партицій** — вона лишається в default і
  видна в метриці (а старіші за retention чистяться батчами після rollup).
- *Не дропати те, чого нема в rollup.* Перед `DROP` партиція ще раз проганяється через `rollups.build` (H2 перераховує
  лише 2 години, тож пропущений запуск інакше назавжди втратив би добу історії). Тест: добу без жодного rollup
  дропнули — історія вціліла.
- *Одночасні менеджери.* `pg_advisory_xact_lock` на створення/дроп.
- *Прив'язаність до H2.* Межа очищення — початок години `now − 7 днів`; партиція дропається, лише коли **вся** лежить
  до цієї межі, тож добу з межею всередині лишаємо (до 8 діб сирих даних).

**Свідомо спрощено / обмеження.** `DROP` бере коротке блокування на батьківську таблицю (`DETACH … CONCURRENTLY`
недоступний, поки існує default-партиція). Міграція копіює кожен рядок один раз в обидва боки — на дуже великій таблиці
запускайте у вікні обслуговування. Тести ганяються на справжньому Postgres (як і весь набір); оскільки вони
виконуються в одній транзакції, а FK відкладений, тести з `DROP` перед ним роблять `SET CONSTRAINTS ALL IMMEDIATE`
(у продакшні задача працює після коміту даних).
