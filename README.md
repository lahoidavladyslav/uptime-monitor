# Uptime Monitor

Django 5 · PostgreSQL · Celery + Redis (+ beat) · server-side templates (Bootstrap CDN).

## Запуск

```bash
docker compose up --build
docker compose exec web python manage.py seed_demo   # demo / demo12345
```

Сайт: http://localhost:8000. Листи про інциденти друкуються в лог `worker-notify`
(`EMAIL_BACKEND=console`).

## Тести

```bash
pip install -r requirements-dev.txt
pytest                     # потрібен Postgres (DATABASE_URL, дефолт postgres://localhost/uptime)
# або в Docker:
docker compose run --rm web pytest
```

Тести не потребують Redis: `config/settings_test.py` ставить locmem-кеш,
`CELERY_TASK_ALWAYS_EAGER=True` і locmem-email. HTTP мокається через `responses`,
час — через `time-machine`. 178 тестів.

## CI та pre-commit

```bash
pip install -r requirements-dev.txt
pre-commit install          # ruff check --fix, ruff format, trailing whitespace, yaml, ...
```

`.github/workflows/ci.yml` (потрібно, щоб `uptime/` був коренем репозиторію):
- **lint:** `ruff check` + `ruff format --check`;
- **test:** Postgres 16 як service-контейнер, `makemigrations --check --dry-run`
  (модель без міграції ламає збірку), `manage.py check`, `pytest`.
Redis у CI не потрібен — тести використовують locmem і eager Celery.
Версія ruff закріплена (`>=0.17,<0.18`) і збігається з `rev` у pre-commit, щоб локально
й у CI правила не розходились.

## Ключові рішення та trade-offs

**N+1 на дашборді.** Один запит: `Subquery` для статусу останньої перевірки й
відкритого інциденту + `Count(filter=Q(...))` для uptime 24 год. Тест
`test_dashboard_has_constant_query_count` фіксує, що кількість запитів не росте з
кількістю моніторів.

**Хто пора перевіряти — у БД.** `schedule_checks` фільтрує через
`F('last_checked_at') + F('interval_seconds') * interval '1s' <= now()`.
`DUE_SLACK = 10 с`: `last_checked_at` — це *початок* перевірки, а beat тікає раз на
хвилину; без запасу 60-секундний монітор «дрейфував» би до перевірки раз на 2 хв.

**Дублі `check_monitor` і блокування.** Три короткі фази:
1. *claim* — один умовний `UPDATE monitors SET last_checked_at=now WHERE id=… AND <пора>`.
   Postgres серіалізує конкурентні апдейти рядка й перераховує `WHERE`, тож із N дублів
   рівно один бачить монітор «простроченим» і виграє; решта виходять (`"skipped"`).
2. *HTTP* — **поза транзакцією**: ні з'єднання з БД, ні рядок не тримаються ≤10 с.
3. *запис* — коротка транзакція з `select_for_update` на моніторі: серіалізує
   відкриття/закриття інциденту й запис результату.

Trade-off: at-most-once на інтервал. Якщо воркер впаде між claim і записом, перевірка
цього інтервалу втрачається (наступна піде за розкладом) — це свідомо замість
довгого локу. «Перевірити зараз» (`force=True`) пропускає умову «пора»; збіг двох
ручних запусків безпечний завдяки локу на фазі запису. Якщо монітор видалили під час
запиту — задача чесно виходить. Чому не Redis-lock: окрема система з TTL, яку треба
узгоджувати з БД; тут стан і так у Postgres.

**Інциденти.** Open/close — всередині того ж локу; частковий `UniqueConstraint`
(`resolved_at IS NULL`) — страховка на рівні БД. Нотифікація йде через
`transaction.on_commit` і передається лише `incident_id`. Email — з
`autoretry_for=(SMTPException, OSError)`, `retry_backoff`, `max_retries=3`.

**Статистика.** Тільки `aggregate`/`Count(filter)`/`Avg`/`Min`/`Max`; без даних —
«немає даних», а не ділення на 0. Смужка 7 днів — один запит
(`TruncDate` + `values` + `annotate`); дні рахуються в UTC.

**Публічна сторінка.** Кешується весь HTML (60 с). Інвалідація — сигнали
`post_save/post_delete` на `Monitor`, двічі: одразу і ще раз в `on_commit` (щоб
конкурентний запит не повернув у кеш старий стан). Збій Redis при інвалідації не
ламає збереження монітора. Обмеження: `queryset.update()` сигналів не викликає —
тому `check_monitor` оновлює `last_checked_at` саме так (інакше кожна перевірка
скидала б кеш), а статус на сторінці може відставати до 60 с. URL і тексти
помилок у шаблон не передаються взагалі.

**Звіти.** Дві згруповані SQL-запити (checks і incidents по `monitor_id`), у Python
лише зливаються рядки моніторів. Простій інциденту обрізається межами періоду
(`Greatest/Least`), відкритий інцидент рахується до «зараз». Статус
`pending → processing` захоплюється атомарним `UPDATE ... WHERE status='pending'`,
тому повторна доставка задачі нічого не робить. Завантаження — через view з
перевіркою власника (`FileResponse`), `/media/` напряму не віддається.

**Очистка.** `cleanup_old_checks` видаляє по `CLEANUP_BATCH_SIZE` id за ітерацію,
підтримується індексом `checked_at`.

**SSRF.** `monitors/security.py`: хост резолвиться, і якщо *будь-яка* адреса не
`is_global` (loopback, RFC1918, link-local/cloud-metadata `169.254.169.254`, CGNAT,
IPv6 ULA, IPv4-mapped IPv6) — URL відхиляється у формі **і повторно перед кожною
перевіркою** (DNS міг змінитись після збереження). Редіректи не відстежуються, тож
обхід через 302 неможливий. Нерезолвний хост не блокується — це просто «down».
`ALLOW_PRIVATE_TARGETS=1` вимикає захист (для локальної розробки). Залишковий ризик:
вузьке вікно DNS-rebinding між нашим резолвом і з'єднанням `requests`; повністю
закрити можна лише підключенням до вже перевіреної IP.

**Rate-limit.** «Перевірити зараз» — не частіше разу на 10 с на монітор (атомарний
`cache.add`; при недоступному кеші дозволяємо, а не 500). Звіти — не більше 3
одночасно в черзі на користувача.

**Графік.** Розмір набору точок обмежений незалежно від кількості перевірок: 24 год —
сирі точки (≤1440), 7 днів — погодинні бакети, агреговані в SQL (≤168). Невдала
перевірка без часу відповіді дає розрив лінії, падіння позначені червоним хрестиком.
Дані передаються через `json_script` (безпечне екранування), без окремого API.

**HTMX-дашборд.** Таблиця опитується раз на 10 с лише поки вкладка видима; сервер на
HTMX-запит віддає тільки фрагмент таблиці (той самий запит, без N+1). Якщо сесія
спливла, у відповідь іде `204 + HX-Redirect` на логін, а не сторінка входу всередині
таблиці. Мінус: опитування, а не push (SSE/WebSocket дали б менше навантаження).

**DNS-rebinding.** Попередня перевірка резолвить хост, але з'єднання резолвить ще раз —
ворожий DNS міг би відповісти «публічною» адресою першого разу і `127.0.0.1` другого.
Тому `monitors/http_client.py` підміняє клас з'єднання urllib3 і перевіряє **адресу
реально підключеного сокета** (`getpeername()`), незалежно від того, що казав DNS.
Перевірено на справжньому TCP-сервері в тестах і в Docker (`redis`, `db`, `web`,
`169.254.169.254` — усе блокується).

**Акаунти** (`accounts/`):
- *Підтвердження email:* новий акаунт `is_active=False`, лист із підписаним
  (`TimestampSigner`, 3 дні) посиланням; повторне надсилання не розкриває, чи існує email.
- *Скидання пароля:* стандартні токени Django; для невідомого email відповідь та сама.
- *2FA (TOTP):* QR/ключ → підтвердження кодом → 8 кодів відновлення (показуються один
  раз, у БД лише SHA-256). Після правильного пароля користувач **ще не залогінений**
  (`pre_2fa` у сесії, 5 хв, ≤5 спроб); код одноразовий (захист від replay через
  `last_used_step`); `next` перевіряється на open-redirect. Вимкнення — за паролем.
  Секрет TOTP шифрується Fernet-ключем поза БД (див. «Безпека акаунтів» нижче).
  Скидання пароля не вимикає 2FA.
- *Залежності:* Dependabot (pip, actions, docker) і `pip-audit` у CI.

**Розширені перевірки.** На моніторі можна задати метод (GET/HEAD/POST), заголовки,
тіло (POST), очікувані коди (`200,204,300-399`) та текст, що має бути у відповіді.
Тіло читається лише коли задано текст, не більше 1 МБ і не довше за загальний
таймаут (захист від «крапельних» серверів). Заголовки `Host`, `Content-Length`,
`Transfer-Encoding`, `Connection` заборонені. Відповідь 200 з неправильним текстом —
це **down**, з окремим повідомленням. Усе, що стосується SSRF, діє й тут.

**SSL-сертифікат.** Щодобова задача (04:00 UTC) читає `notAfter` через guarded-сокет,
шле один лист на кожен поріг (14 днів → 3 дні → прострочений) — `ssl_alerted_level`
захоплюється умовним `UPDATE`, тому два воркери не продублюють лист; після
продовження сертифіката стан скидається. Невалідний/прострочений сертифікат
показується на сторінці монітора.

**Вікна обслуговування.** У вікні перевірки **не виконуються** (ні за розкладом, ні
«Перевірити зараз»), тож цей час не рахується простоєм, а на публічній сторінці
показується «Планові роботи». Обмеження: інцидент, відкритий до початку вікна,
залишається відкритим, поки перевірка не відновиться після вікна.

**Публічні сторінки** (`monitors/public.py`):
- *Один монітор* `/status/<slug>/` і *група* `/page/<slug>/` (модель `StatusPage`, M2M до
  моніторів власника — форма пропонує лише свої). Є назва, опис, логотип (лише http/https),
  загальний банер (працює / частковий збій / збій / планові роботи), смужка 7 днів і
  історія інцидентів за 30 днів **без текстів помилок і URL**.
- *Запити:* незалежно від кількості моніторів — константа (`daily_bars`, `uptime_by_monitor`
  групують по `monitor_id` в одному запиті); тест фіксує стелю.
- *Кеш:* 60 с, інвалідація сигналами при збереженні/видаленні монітора, вікна
  обслуговування, сторінки та зміні складу групи (двічі: одразу і в `on_commit`).
  Видалення монітора інвалідує й групи, до яких він входив (`pre_delete`, поки зв'язки ще є).
- *Підписка:* Atom-стрічка `/status/<slug>/feed/` і `/page/<slug>/feed/`. Для інциденту
  два записи (початок і відновлення) з різними `guid`, щоб читалка показала новий запис
  про відновлення. `Cache-Control: max-age=60`. Email-підписки не робив: це double-opt-in,
  токени відписки й антиспам — окремий обсяг.

## Експлуатація

**Production-стек** (`docker-compose.prod.yml`, `Dockerfile.prod`, `deploy/nginx.conf`):

```bash
cp .env.example .env.prod      # заповнити SECRET_KEY, ALLOWED_HOSTS, паролі, SMTP
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

- gunicorn за nginx; статика збирається при збірці образу й віддається WhiteNoise
  (S3 не потрібен: медіа — лише звіти, які віддаються через view з перевіркою власника).
- `DJANGO_ENV=production` вмикає fail-fast: без `SECRET_KEY` і `ALLOWED_HOSTS` застосунок
  **не стартує**; `DEBUG` примусово вимкнений; Secure-cookies, HSTS, SSL-redirect
  (`/healthz/` виключений, бо проби приходять по HTTP). `manage.py check --deploy` без
  попереджень (перевіряється тестом). HSTS-preload — лише за явним `HSTS_PRELOAD=1`.
- Контейнер працює від непривілейованого користувача; міграції — окремий one-shot сервіс,
  від якого залежать усі інші. TLS термінується **перед** nginx (балансувальник/Caddy),
  який має виставляти `X-Forwarded-Proto`.
- nginx: `limit_req` на `/login|signup|password-reset|confirm` (429 після ліміту).
- Брокер і кеш Celery — окремі Redis-бази (`REDIS_URL` / `CACHE_REDIS_URL`).

**Окремі черги й воркери.** `checks` (цикл перевірок, SSL, rollup), `notifications`
(листи), `reports` (CSV, `-c 1 -O fair`, `prefetch=1`). Довгий звіт ніколи не стоїть
перед перевіркою або листом. Перевірено вживу: кожне завдання потрапляє у свій воркер.

**Спостережуваність:**
- `GET /healthz/` — 200, якщо веб-процес бачить БД і кеш (інакше 503). Поле `checks: stale`
  показує, що фоновий конвеєр (beat → worker) мовчить, але **код відповіді не змінює**:
  перезапуск web не оживить мертвий worker.
- `GET /metrics/` — Prometheus-формат, **вимкнений, поки не задано `METRICS_TOKEN`**,
  далі Bearer-авторизація (порівняння за постійний час). Метрики: монітори за станом,
  відкриті інциденти, перевірки за 5 хв, статуси звітів, SSL ≤14 днів і
  `uptime_scheduler_lag_seconds` — вік найбільш простроченої перевірки: зростає, коли
  зупинилися beat або воркери (основний алерт). Кількість запитів не залежить від числа моніторів.
- Sentry — лише якщо задано `SENTRY_DSN` (`send_default_pii=False`).
- **Структуровані логи.** У production — один JSON-рядок на подію (`LOG_FORMAT=json|plain`
  перевизначає), у dev — звичайний текст. Кожен рядок має `request_id` (з заголовка
  `X-Request-ID`, якщо він безпечний, інакше генерується; повертається у відповіді) або
  `task_id` для Celery. Access-лог пише **шаблон маршруту** (`confirm/<str:token>/`), а не
  сирий шлях — токени підтвердження/скидання/відписки лежать в URL; пише `user_id`, але
  ніколи email, query-рядок чи тіло. Стандартний `django.request` (він друкує сирі шляхи
  для кожного 4xx) приглушений до ERROR, gunicorn access-log вимкнений. `/healthz/` не логується.
  IP клієнта береться з `X-Real-IP` лише в production (його виставляє наш nginx;
  `TRUST_PROXY_HEADERS`). Якщо перед nginx є ще один балансувальник — налаштуйте real_ip.
- **Журнал входів.** `LoginEvent` пишеться з Django-сигналів автентифікації (веб і API
  користуються одним `login()`), плюс невдалі коди 2FA та блокування. Видно власнику на
  «Безпека акаунта» і в `GET /api/v1/account/login-events`; зберігається 90 днів.
  Спроби з **невідомим логіном у БД не пишуться** (шум від ботів, а в полі логіну люди
  часто вставляють пароль) — лише в лог, без імені.

**Безпека акаунтів.**
- **TOTP-секрети шифруються в БД** (Fernet, випадковий IV на кожен запис; ключ у
  `TOTP_ENCRYPTION_KEYS` поза базою). Дамп БД сам по собі більше не дає генерувати коди.
  У production без ключа застосунок не стартує, неправильний формат теж ловиться на старті.
  Ротація: додати новий ключ *першим* (`new,old`), задеплоїти, пізніше прибрати старий. Втрата
  ключа = користувачі налаштовують 2FA заново (кошти відновлення — коди відновлення). У dev
  ключ виводиться з `SECRET_KEY`. Міграція `0003` шифрує наявні рядки (ідемпотентна).
  Обмеження: ключ і код живуть в одному середовищі; для вищого рівня — KMS/секрет-менеджер.
- **Реєстрація не розкриває, чи є email у системі.** Нова адреса, непідтверджений акаунт і
  активний акаунт отримують однакову відповідь; у другому випадку піде повторний лист
  підтвердження, у третьому — лист власнику «у вас уже є акаунт» з посиланням на відновлення.
  Логін, що вже зайнятий, **досі повідомляється** (це неминуче, поки логін унікальний і
  показується); нагромаджується лише nginx-лімітом.
- Swagger і `openapi.json` у production **закриті** (`API_DOCS=1` вмикає). Контракт для
  фронтенду береться з файлу в репозиторії, а не з живого сервера.

**Email-підписки на статус-сторінки.** Публічні сторінки (групова й окремого монітора) мають
посилання «Сповіщення на email» → окрема *некешована* форма (в кешованій сторінці не може бути
CSRF-токена). Double opt-in: лист із посиланням (3 дні), без підтвердження листів немає, а
непідтверджені рядки чистяться щодоби. Відповідь на форму однакова для нової, очікуючої й уже
підтвердженої адреси (не можна дізнатися, хто підписаний); повторний лист — не частіше ніж раз
на 10 хв на адресу, 10 запитів/год на IP, не більше 5000 підписників на сторінку. Відписка —
посилання в кожному листі + `List-Unsubscribe` / `List-Unsubscribe-Post` (RFC 8058, one-click).
GET-посилання відписки лише показує кнопку: поштові сканери відкривають лінки й не повинні
відписувати людей. Листи містять **лише публічні дані** (публічна назва, час, тривалість) — без
URL моніторингу й тексту помилки. Один лист на адресу, навіть якщо вона підписана і на групу,
і на монітор. Посилання в листах будуються від `SITE_URL`.

**Погодинні агрегати.** `HourlyStat` (монітор × година: total/up/сума часу) рахується щогодини
останні 3 години **ідемпотентно** (upsert одним запитом) і переживає 30-денне очищення
сирих перевірок (зберігається 400 днів). На сторінці монітора — uptime за 30/90 днів. Для
наявних даних: `manage.py backfill_rollups` (лише додає відсутні години, нічого не
перезаписує). Партиціювання `CheckResult` не робив: з очищенням за 30 днів і агрегатами
таблиця обмежена, а партиції варто додавати, коли виміри покажуть потребу.

## Frontend (SPA, `frontend/`)

React 18 + TypeScript + Vite + Tailwind; говорить з `/api/v1/` сесійними cookie + CSRF (один origin,
без CORS). Старий Django-інтерфейс на `:8000` лишається робочим.

```bash
docker compose up -d --build        # frontend на http://localhost:5173 (проксі /api -> web)
# або локально:
cd frontend && npm ci && npm run dev    # потрібен бекенд на :8000
npm test -- --run                        # Vitest + Testing Library + MSW
npm run lint && npm run typecheck && npm run build
```

**Контракт не може розійтися.** Типи `src/api/schema.d.ts` генеруються з `api/openapi.json`
(`npm run gen:api`). Змінили API → `python manage.py export_openapi` → `npm run gen:api` → коміт обох файлів.
CI падає, якщо знімок або типи застарілі (`export_openapi --check`, `git diff --exit-code`).

**Production:** задайте `FRONTEND_URL` (див. `.env.example`): листи підтвердження й скидання пароля з API
ведуть на SPA. nginx обмежує перебір на `/login|signup|…` і на `/api/v1/auth/(login|signup|…)`.

Етап 1: вхід (з 2FA), реєстрація, підтвердження email, скидання пароля, дашборд.
Етап 2: **сторінка монітора** (`/monitors/:id`, вкладки в `?tab=`): картки uptime 24 год/7/30/90 днів,
графік часу відповіді (Recharts, підвантажується лише тут; збої = розрив лінії + червоні точки),
статистика за період, SSL, вікна обслуговування (створення/видалення; час вводиться локальний, на сервер
йде UTC), перевірки (пагінація, фільтр «лише падіння» на сервері), інциденти, «Перевірити зараз»
(клієнтська пауза 3 с + серверний cooldown → 429, обслуговування → 409). Чужий або неіснуючий id → 404.
Решта екранів (форма монітора, статус-сторінки, звіти, безпека) — етапи 3–4, поки що заглушки.
Версії vite/vitest/msw закріплені під Node 20 (новіші мажорні вимагають Node ≥ 22.12).

## API-контракт (для нового фронтенду)

`/api/v1/` (Django Ninja) → схема на `/api/v1/openapi.json`; знімок лежить у `api/openapi.json` і
**є контрактом**: з нього генеруються TypeScript-типи фронту (`frontend`, `npm run gen:api`).

```bash
python manage.py export_openapi          # оновити знімок після зміни API
python manage.py export_openapi --check  # падає, якщо знімок застарів (запускається в CI і в pytest)
```

Помилки валідації завжди `422 {"message": ..., "errors": {поле: [повідомлення]}}` (`"__all__"` — загальні).
Усі небезпечні запити без автентифікації (логін, реєстрація, скидання пароля) захищені CSRF так само,
як автентифіковані: auth-клас `csrf_protect` спрацьовує до розбору тіла.

## Відомі обмеження / що б робив далі

- Підписники не мають особистого кабінету: керування лише через посилання в листах; власник не бачить їх список (лише через адмінку).
- Немає листа «новий вхід з невідомого пристрою» — журнал лише показується.
- `allow_redirects=False`: 3xx вважається «up» за ТЗ, редірект не відстежується.
- Статика/медіа віддаються dev-сервером; для продакшну — gunicorn + nginx/S3.
